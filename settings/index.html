Data Watchdog

Know when your sources stop reporting. An unchanged measurement alone is not a sign of failure.

How to use Data Watchdog

What does Data Watchdog do?

Data Watchdog checks whether a device or integration still shows valid activity or data delivery. It does not simply check whether a measurement changes: a temperature can stay at 21.3 °C while the sensor works perfectly.

Quick start

  1. Choose Add monitor above the list, then choose how to check for updates.
  2. Open Select devices, choose one or more sources, then confirm with Use selection.
  3. Enter how often updates are normally expected.
  4. Set the timing once for your selection. Open Adjust settings per device only when a source needs different timing.
  5. Choose Add monitors. Fields needing attention will be highlighted.
  6. For phone notifications, create a Homey Flow using Any watchdog incident started.
Choosing a monitoring method

Device activity

Checks whether Homey has seen the device recently.

This proves activity, not necessarily a new measurement or successful delivery.

Last data received

Use this when the device or app keeps track of when new data was last received.

The selected field must itself contain a date/time value updated by the source. A measurement value or its lastUpdated metadata is not a substitute. If several fields are selected, a new time in any one counts as an update.

Flow confirmation

Let a Homey Flow confirm after a successful update that everything is still working.

The confirmation must follow a real successful update. A blind repeating timer does not prove that the source works. Existing API confirmations remain supported.

Choosing the timing

Expected update interval: how often should the source normally report activity or new data?

Consider stale after: how long may no valid update arrive before the source is treated as stale?

For updates every 5 minutes, you might expect an update every 5 minutes and alert after 15 minutes. Allow some margin for delays. The timeout must be at least the expected interval. Device activity and Last data received require at least 2 minutes.

The input arrows move in half-minute steps: 0.5 is 30 seconds; 1.5 is 90 seconds. A short confirmation period means an incident notification may follow slightly after the timeout. Recovery also needs to remain stable before the incident closes.

Understanding monitor statuses
WARMING_UP
Waiting for a fresh update after setup, restart or a change to how freshness is checked.
HEALTHY
Recent valid activity or data delivery has been confirmed.
SUSPECTED_STALE
The signal is overdue. Data Watchdog waits briefly before declaring an incident.
DEVICE_STALE
The device has missed the configured stale period and an incident is active. It may be grouped with other devices from the same integration.
RECOVERING
Fresh updates have returned; waiting for stable recovery before closing the incident.
DISABLED
Monitoring is turned off for this monitor.
MISSING
The configured device or required timestamp field cannot currently be found.
UNKNOWN
A reliable state cannot currently be determined, for example because observation is unavailable.
Getting phone notifications

Data Watchdog detects incidents; it does not automatically send everyone a push notification. Create a Homey Flow to choose who receives messages and which incidents to report.

  1. WHEN: Data Watchdog → Any watchdog incident started.
  2. THEN: Homey → Send a push notification. Choose the recipient and message.

For an optional recovery message, create a second Flow using Any watchdog incident recovered. You can use the device and integration information supplied by the trigger in your message. Avoid sending the same notification from both a general incident trigger and a device-specific trigger.

If several monitors from the same integration stop reporting together, Data Watchdog can group them into one integration incident.

Using the optional Local self-test

Pair Data Watchdog Test Source (simulation) only if you want a safe local test of stale detection, recovery and your notification Flows. It does not control production devices and is not needed for daily monitoring. Test incidents can send real notifications through your existing watchdog Flows.

  • Start heartbeat: sends a heartbeat now, then every 30 seconds.
  • Stop: stops the heartbeat and freezes the test timestamp.
  • Send once: sends one heartbeat without starting a stopped simulator. An already running simulator stays running.
  • After an app restart, the simulator deliberately starts STOPPED.

For a first test, monitor the test device with Last data received, Last test heartbeat, ISO format, a 0.5-minute expected interval and a 2-minute timeout.

Editing and Technical note

Edit changes the existing monitor; Save changes keeps it, while Cancel discards the draft. Changing the freshness method or timing starts a new observation period. Disable pauses monitoring.

Technical note is optional. Use it to remember why you trust a freshness signal. It does not affect detection or restart monitoring.

If something does not look right

Use Refresh status. If WARMING_UP persists, check that the chosen source is producing new updates. For MISSING, check the device and timestamp field still exist. A normal rename alone does not remove a monitor.

If Last data received never becomes HEALTHY, check the selected field, format and whether its time moves forward. If Device activity stays UNKNOWN, Homey may not provide a usable last-seen time.

If no phone notification arrives, check your incident Flow, its conditions, recipient and Homey push permissions.

Important limitations

Monitoring is only as trustworthy as the selected freshness signal. A wrong time field can make an unhealthy source appear healthy. An unchanged measurement is not proof of a fault, and activity is not proof of new measurement data.

If the whole Homey stops running, Data Watchdog on that same Homey cannot report its own outage. Monitoring the entire host requires a separate solution outside that Homey; this app does not provide that external monitoring.
